# Security model

This document states what mailbrief trusts, what it does not, and which risks are
accepted rather than mitigated. It is written to be falsifiable: every claim maps
to a specific line of behavior you can verify in `mailbrief.py`.

## Trust boundaries

```
  ┌─────────────────────────────── your machine ───────────────────────────────┐
  │                                                                            │
  │   macOS Keychain ──secret──▶ mailbrief ◀──HTTP :11434──▶ Ollama            │
  │                                  │                                         │
  │                                  │ writes                                  │
  │                                  ▼                                         │
  │                            ~/.mailbrief/                                   │
  └──────────────────────────────────┬─────────────────────────────────────────┘
                                     │
                     ┌───────────────┴───────────────┐
                     │ IMAP/TLS          HTTPS       │
                     ▼                               ▼
              your mail provider         Greenhouse / Lever / Ashby
                (authenticated)              (public, unauthenticated)
```

Everything inside the box is local. The only outbound traffic is an authenticated
IMAP/TLS session to your mail provider and unauthenticated HTTPS GETs to public
job-board endpoints. Message content is never transmitted anywhere.

## Controls

### Credential handling

The IMAP secret is read from the macOS login keychain via `security
find-generic-password` at the moment of use. It is never written to a dotfile,
never placed in an environment variable, and never logged.

Use a provider-issued app password, not your account password. An app password is
scoped to mail access and revocable independently, which bounds the blast radius
of a compromised keychain to "read this mailbox" rather than "full account
takeover."

### Read-only mailbox access

Every IMAP fetch passes `mark_seen=False`. There is no code path that sends,
deletes, moves, or flags a message. The worst outcome of a logic bug is an
incorrect markdown file.

This is a deliberate design constraint, not an accident of scope. See *Prompt
injection* below for why it matters more than it appears to.

### Idempotency

Processed message UIDs are committed to SQLite before the next fetch, so a crash
mid-run resumes cleanly and no message is processed twice.

IMAP UIDs are only stable within a folder's `UIDVALIDITY` epoch. If the provider
resets it, delete `state.db` and reprocess — the cost is one extra run.

### No egress of message content

Inference is local. Verify this yourself:

```bash
# While a triage run is in flight, confirm the only connections are
# IMAP/TLS to your provider and loopback to Ollama.
lsof -i -P | grep -i python
```

## Residual and accepted risks

### Prompt injection via email body — ACCEPTED

An attacker who can send you email controls text that reaches the model. They can
influence the `summary`, `action`, and `category` fields in your brief — for
example, by embedding instructions in white-on-white HTML.

This is accepted because the model has no tools, no network access, and no write
path beyond the brief file. The worst achievable outcome is a misleading or
alarming line of text in a document you read.

**This risk changes character entirely if you extend the tool.** Adding send,
delete, archive, or auto-reply capability converts a nuisance into a real attack:
the untrusted content would then be steering a privileged action. If you add any
write capability to the mailbox, re-derive this section first. Do not treat
`summary` as trusted input to anything.

### Model-fabricated claims in drafts — MITIGATED BY PROCESS

Cover-letter drafts are generated by a small local model. Models in this size
class occasionally assert experience the candidate does not have, regardless of
prompt constraints.

The system prompt forbids invention explicitly, and every generated draft carries
a verification checklist as its first section. That is a process control, not a
technical one. Read the draft.

### Data at rest — RESIDUAL

`~/.mailbrief/` contains message summaries, sender addresses, subject lines, your
resume, and generated drafts in plaintext.

- FileVault covers at-rest encryption for the disk.
- Exclude `~/.mailbrief/` from any cloud-synced directory.
- `.gitignore` excludes `state.db`, `resume.txt`, `briefs/`, and `drafts/`, so
  these never enter version control. Verify before your first commit.

### Supply chain — RESIDUAL

Two direct dependencies: `httpx` and `imap-tools`. Both are widely used and
actively maintained. Pin them (`requirements.txt`) and review transitive updates
rather than tracking floating versions.

The installer fetches Ollama via Homebrew and pulls a model from the Ollama
registry. Both are trust decisions you are making about those publishers.

### Job board endpoints — LOW

Responses from Greenhouse, Lever, and Ashby are untrusted input and are treated
as such: HTML is stripped, content is truncated, and the text reaches only the
scoring and drafting prompts. The same injection reasoning as email applies, with
the same bounded consequence.

## Compliance notes

For personal use this sits outside most regulatory scope. If you adapt it for an
organization's mail:

- **GDPR / similar** — you are processing personal data (sender addresses,
  message content). Local processing avoids a transfer, but retention still
  applies: `state.db` and `briefs/` grow without bound. Add a retention policy.
- **SOC 2 / ISO 27001** — the keychain dependency means this is tied to one
  user's login session and is not suitable as shared infrastructure without
  rework of the credential path.
- **Shared or delegated mailboxes** — the read-only guarantee holds, but summaries
  of other people's correspondence landing in a local plaintext file is a
  disclosure question your policy may already answer.

## Reporting

This is a personal-scale tool with no security support commitment. If you find a
flaw, open an issue. Do not include real message content or credentials in the
report.
